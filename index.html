CASE-001 TryHackMe Lab - Data Exfiltration Through DNS Tunneling verified ▸

DNS Exfiltration takes advantage of the Domain Name System Protocol because it's packets or traffic is normally allowed in computer networks. Attackers use it to smuggle data through encoding of bytes in DNS queries/responses, which makes it hard for firewalls and web proxies to discover.

Tools
Wireshark, Splunk
Steps
  1. Open the captured network traffic pcap file in Wireshark.
  2. Filter for dns.
  3. Filter for dns with no response: "dns.response.code == 0" to check whether there are any queries with large query length.
  4. Narrow down the search by filtering further for long suspicious subdomain lengths: "dns && frame.len > 70"
  5. Filter on the suspicious domain receiving the dns requests: "dns && dns.qry.name contains"suspiciousdomain"
  6. Do a correlation in splunk: "index=data_exfil sourcetype=DNS_logs"
  7. Display the statistics of dns queries generated per user using: index="data_exfil" sourcetype="DNS_logs" | stats count by src_ip
  8. Apply another filter to identify the suspicious ones: index="data_exfil" sourcetype="dns_logs" | stats count by query | sort -count
Findings
  1. Large number of dns requests without repsonses.
  2. Large length of dns query.
Recommendation
Block the suspected domain and Ip through the firewall
CASE-002 Phishing email triage — Header and Attachment analysis verified ▸

Analyzed a TryHackMe phishing email sample: reviewed the full header chain, checked the sender domain's authentication (SPF/DKIM/DMARC), and analyzed the attached file.

Tools
Email header analyzer, VirusTotal, urlscan.io
Steps
  1. Investigated the email headers and analyzed the embedded URL.
  2. Identified the recipient and any suspicious elements.
  3. Analyzed the message source to identify the sender's ip.
  4. Investigated the identified ip to determine its owner.
  5. Ran an SPF check on the return-path domain identified in the headers.
  6. Ran a DMARC lookup for the return-path domain found in the headers to identify the complete DMARC record.
  7. Noted the file name of the attached file.
  8. Downloaded the attached file and generated a hash.
  9. Ran the hash through VirusTotal to check for any malicious verdicts.
Findings
  1. The sender domain failed SPF and DKIM authentication checks.
  2. The attached file was identified as malicious by VirusTotal.
  3. The threat categories identified by VirusTotal were: Trojan, and Ransomware.
Recommendation
Block the sender domain and quarantine the email.
CASE-003 TryHackMe Lab - Data Exfiltration Through FTP. verified ▸

Attackers use FTP to move large amounts of data off a network, sometimes via compromised credentials, misconfigured servers, or temporary accounts. Detection relies on a mix of packet inspection (FTP only), server logs, SSH session metadata, and network flow/size/pattern analysis.

Tools
Wireshark
Steps
  1. Look for FTP sessions using Wireshark filters: "ftp || ftp-data" to isolate ftp control traffic.
  2. Filter to show only login attempts with USER/PASS: ftp.request.command == "USER" || ftp.request.command == "PASS" and look for suspicious usernames or weak passwords.
  3. Look for anomalies in filenames or credentials: ftp contains "STOR".
  4. Right-click on a packet and select "Follow" > "TCP Stream" to view the FTP communication.
  5. Look for suspicious files by filtering using file extensions: ftp contains "csv"
  6. Look for traffic with large lengths using: ftp && frame.len > 90 and check the tcp stream.
Findings
  1. Sensitive data was found being transferred via FTP in different file formats.
Recommendation
Block the identified malicious ip addresses.
CASE-004 TryHackMe Lab - Data Exfiltration Through HTTP. verified ▸

Data exfiltration via HTTP is when an attacker moves sensitive data out of a target network using HTTP as the transport. HTTP is commonly abused because it blends with normal web traffic, can traverse firewalls and proxies, and can be obfuscated through encoding, encryption and tunneling.

Tools
Wireshark, Splunk
Steps
  1. Search for the http logs in Splunk using: index="data_exfil" sourcetype="http_logs".
  2. Narrow down the results to focus on POST requests: index="data_exfil" sourcetype="http_logs" method=POST.
  3. Investigate the average size of data sent to various domains: index="data_exfil" sourcetype="http_logs" method=POST | stats count avg(bytes_sent) max(bytes_sent) min(bytes_sent) by domain | sort - count
  4. Filter for requests with large payload sizes: index="data_exfil" sourcetype="http_logs" method=POST bytes_sent > 600 | table _time src_ip uri domain dst_ip bytes_sent | sort - bytes_sent
  5. Depending on the findings, correlate with the pcap to further investigate.
  6. In Wireshark, filter for http traffic: http
  7. Filter for POST requests: http.request.method == "POST"
  8. Look for traffic with frame length exceeding 500: http.request.method == "POST" and frame.len > 500
  9. Increase the frame length size to 750 to further reduce the noise.
  10. The previous step reveals only one suspicious request entry.
Findings
  1. Sensitive data was found being transferred via http through .txt and tar.gz files.
Recommendation
Isolate the identified internal host ip addresses and block the identified malicious ip addresses.
CASE-005 TryHackMe Lab - Data Exfiltration Through ICMP. verified ▸

The Internet Control Message Protocol (ICMP) operates at the network layer and is used for diagnostic and control functions, including ping and TTL-exceeded notifications. Because it is frequently allowed through firewalls and subjected to less scrutiny than TCP or UDP traffic, ICMP is a known vector for data exfiltration and tunneling. Threat actors embed data within ICMP packet payloads and transmit it to an attacker-controlled listener.

Tools
Wireshark
Steps
  1. Open the captured pcap file in Wireshark and filter for icmp traffic: icmp
  2. Look for unusually frequent and/or large icmp echo requests/replies.
  3. Isolate echo request packets: icmp.type == 8
  4. Apply another filter on the isolated packets and focus on frame length > 100: icmp.type == 8 and frame.len > 100: Any packet with over 100 bytes is suspicious. Normal pings range ~74 bytes total.
  5. Right-click on a suspicious packet and select "Follow" > "ICMP Stream" to view the communication.
Findings
  1. Sensitive data was found being transferred via ICMP in .txt files.
Recommendation
  1. Isolate the identified internal host ip addresses and block the identified malicious ip addresses.
  2. Restrict outbound ICMP traffic from the identified internal hosts.
  3. Use IDS/IPS rules to flag abnormal payload sizes or content in ICMP packets.
  4. Limit ICMP packet size and rate to reduce the risk of data exfiltration.
  5. Create a baseline for normal ICMP traffic patterns so that anomalies can be detected.

Detection artifacts

rules & queries
sigma — excessive_failed_logins.yml
title: Excessive Failed Logins From Single Source
status: experimental
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4625
  timeframe: 5m
  condition: selection | count() by IpAddress > 10
level: medium

Flags more than 10 failed logon events (Event ID 4625) from one source IP within a five-minute window. Written after CASE-001, and tuned against a normal-use baseline from my own lab to reduce noise from mistyped passwords.

splunk — spl query
index=windows EventCode=4625
| stats count by src_ip, dest_user
| where count > 10
| sort - count

Same logic as a Splunk search, for environments running Splunk instead of an ELK stack.
